# 时钟回拨导致握手静默丢失 — 根因分析与修复交付说明

## 1. 根因链

### 1.1 时间戳的三层语义

| 层 | 位置 | 语义 | 承担职责 |
|---|---|---|---|
| 生成层 | `tai64n/tai64n.go` `Now()` / `stamp()` | 发起端**本机墙钟**编码为 TAI64N（12 字节大端：秒 + 纳秒），在 `CreateMessageInitiation` 中以 AEAD（密钥派生自 static-static DH）加密进 `MessageInitiation.Timestamp` | 提供**已认证**的时间戳：第三方无法伪造，只能原样重放旧报文 |
| 传输/状态层 | `device/noise-protocol.go` `Handshake.lastTimestamp` | 响应端按对端记录**已接受时间戳的高水位线**（per-peer，纯内存，重启清零） | 把"严格递增"判定物化为单值比较，无需保留历史报文 |
| 判定层 | `ConsumeMessageInitiation` 重放门 | `replay := !timestamp.After(handshake.lastTimestamp)`，非严格递增即判重放，**静默 return nil** | 防重放：同一（或更旧）的 initiation 不得再次建立会话 |

关键事实：三层中**没有任何一层使用响应端本机时钟**。判定层的输入全部来自发起端墙钟（当前报文时间戳 vs 高水位线中保存的历史发起端时间戳）。

### 1.2 为什么回拨后的新握手撞上重放门

持久失效的充要条件是：**回拨前记录的 `lastTimestamp` 高于回拨后发起端时钟生成的任何新时间戳**。典型路径：

1. 回拨前，服务机器时钟偏快（NTP 未校正、快照后漂移等），握手把时间戳 `T_fast` 记入对端高水位线；
2. 时钟回拨发生（NTP 步进校正、管理员改时间、VM 快照回滚后时钟被重置），发起端时钟回到真实时间 `T_real < T_fast`；
3. 此后每个新 initiation 的时间戳 `≈ T_real`，永远 `!After(T_fast)`，直到真实时间自然走过 `T_fast`（可能数小时）；
4. 每个新握手在判定层命中重放门，被静默丢弃。

报文本身**完全合法**：AEAD 校验通过、静态密钥认证通过——它只输在"时间戳不递增"这一条上。

### 1.3 为什么全程无错误信号

- 响应端：重放门 `return nil` 前只有一行 `Verbosef` 日志（`device.log.Verbosef("...handshake replay...")`），默认日志级别不可见；协议层面**没有任何错误报文**可回给发起端（WireGuard 协议无 handshake error 消息类型）；
- 发起端：收不到响应，按 `RekeyTimeout=5s` 重试，`MaxTimerHandshakes = 90/5 = 18` 次（`RekeyAttemptTime=90s`）后放弃，`FlushStagedPackets()` 清空待发队列——放弃动作此前也只有 `Verbosef` 日志（`device/timers.go`）；
- 数据面：现有 keypair 在 `RejectAfterTime=180s` 后过期作废，隧道在无任何 error 级信号的情况下中断。

### 1.4 触发条件与影响范围

**触发条件**（任一）：发起端时钟 NTP 步进回拨、管理员回拨系统时间、VM 快照回滚/挂起恢复导致时钟重置——且回拨前已有握手把"偏快"的时间戳记入对端高水位线。

**影响范围**：该对偶关系的**新握手全部失败**，持续时长 = 回拨幅度（直到真实时间追平旧高水位线）；已建立会话在 180s 密钥过期后中断；待发数据被清空。重启任一端可恢复（高水位线为纯内存态），但不重启则持续静默中断。

## 2. 修复方案

### 2.1 核心观察

时间戳经 AEAD 认证，攻击者**无法伪造**新 initiation，只能**逐字节重放**旧报文。因此"重放"与"回拨后的新握手"在两点上可区分：

1. **时效性**：回拨校正后的新握手时间戳 ≈ 真实当前时间；重放的旧报文时间戳是过去某个时刻；
2. **临时公钥新鲜度**：新握手携带全新的随机 ephemeral；重放报文的 ephemeral 此前必然出现过。

### 2.2 改动

**响应端恢复路径**（`device/noise-protocol.go` `ConsumeMessageInitiation`）：

- 严格递增主门**保持不变**：`timestamp.After(lastTimestamp)` 仍是常规接受条件，高水位线只升不降；
- 新增恢复门：时间戳未过主门时，仅当同时满足
  1. 时间戳落在本机墙钟 ±`HandshakeTimestampMaxSkew`（300s，`device/constants.go`）窗口内——报文"声称自己是新的"；
  2. ephemeral 不在本对端最近接受的 ephemeral 环形缓存（256 项，截断为 uint64，纯内存）中——不是逐字节重放；
  
  才接受该握手，并以 **error 级日志**记录恢复事件（对运维可观测）；
- 恢复接受**不回退** `lastTimestamp` 高水位线；之后发起端时钟生成的时间戳持续递增，直至自然超过旧高水位线后回到主门路径；
- 每次接受（主门或恢复门）都把 ephemeral 记入环形缓存。

**发起端可观测信号**（`device/timers.go`）：重试 18 次耗尽放弃时的日志由 `Verbosef` 升为 `Errorf`——即使恢复路径因极端时钟偏斜（>300s）失效，发起端也有可观测的失败信号，不再静默中断。

**辅助**：`tai64n` 包导出 `FromTime`/`Before`；`CreateMessageInitiation` 的时间戳生成改为可注入的 `tai64nNow` 变量（仅供测试模拟回拨）。

### 2.3 验收口径逐条核对

| 验收要求 | 落实 |
|---|---|
| 回拨后新握手被接受或可观测失败 | 恢复门接受（主路径）；极端偏斜下发起端 error 级放弃日志（兜底） |
| 严格递增语义不削弱 | 主门与高水位线逻辑原样保留；恢复门只额外接受"已认证 + 声称新鲜 + ephemeral 未见"的报文——此类报文只能由合法对端实时生成；旧重放出窗口即拒，近期重放 ephemeral 命中即拒 |
| 不引入跨重启持久态 | ephemeral 环形缓存为 per-peer 纯内存，重启清零（与高水位线一致） |
| 不引入未认证报文放大面 | 恢复判定全部在 AEAD 解密**之后**执行，只处理已认证报文；不新增任何响应报文类型；flood 限流（50ms/对端）与 cookie 机制原样生效；缓存仅在接受时写入，攻击者无法用重放冲刷 |
| 隧道不静默中断 | 恢复接受记 error 日志；重试耗尽记 error 日志 |

### 2.4 恢复路径取舍的理由

选择"响应端带护栏接受"而非"协议内失败信号"，理由：

1. **协议无错误报文设施**：新增错误消息类型要改动线协议（破坏互操作），且对未认证输入回包会引入放大面——恰是验收禁止的；
2. **恢复接受密码学上安全**：响应端每次响应都生成全新 ephemeral，即使接受了重放，派生的会话密钥也是新的、攻击者不可得；真正的风险仅是状态搅动/CPU，已由 flood 限流与 cookie 机制覆盖；
3. **偏斜窗口 + ephemeral 缓存双重护栏**使恢复门实际接受集合 = "合法对端在窗口内实时生成的报文"，与严格递增语义在威胁模型上等价；
4. **窗口取值 300s**：只需覆盖对端间残余时钟偏斜（NTP 环境下通常 <1s），无需覆盖回拨幅度本身——回拨校正后时间戳即回到真实时间附近。VM 快照回滚后、NTP 尚未校正期间（时钟停留在快照时刻）的报文仍被拒绝，这是有意的：那些时间戳确实是旧的，且该窗口是暂态，NTP 校正后恢复路径即生效。

## 3. 回归测试

`device/noise_clockrollback_test.go` `TestNoiseHandshakeClockRollback` 端到端覆盖：

1. 正常握手建会话；
2. 模拟回拨：把响应端高水位线置为未来 1 小时；
3. 发起端连续 3 次重试新握手（模拟 5s 重试节奏，绕过 flood 限流）——**必须全部接受**（修复前全部静默丢弃）；
4. 断言高水位线未回退；
5. 逐字节重放已接受的 initiation——**必须拒绝**；
6. 完成回拨后的握手并双向加解密验证数据面恢复；
7. 注入 1 小时前的陈旧时间戳（窗口外、全新 ephemeral）——**必须拒绝**。

- `go test ./device/ -race` 全量通过（含新回归测试与既有 `TestNoiseHandshake`）；
- `go test ./...`：除 `tun` 包外全部通过；`tun` 包失败为既有 Windows 编译问题（`checksum_test.go` 引用 `unix.IPPROTO_TCP`），与本题无关，不在验收范围；
